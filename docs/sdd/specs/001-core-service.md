## Context

An automotive parts distributor needs to manage the inputs used for replenishment
decisions and rank parts by urgency. Current stock and working capital are
limited, while sales, supplier lead time, and operational criticality differ by
part.

The first version must provide a maintainable HTTP service whose domain rules are
independent from HTTP and PostgreSQL. See the
[project overview](../../project-overview.md) for broader context and the
[system design](../../architecture/system-design.md) for architecture.

## Problem statement

Inventory operators do not have a consistent, auditable way to determine which
parts are expected to fall below minimum stock during supplier lead time. The
service must persist part information and return a deterministic priority ranking
based on the supplied business formulas.

## Goals

- Provide complete CRUD behavior for parts.
- Allow optional category filtering when listing parts.
- Identify all persisted parts that need replenishment.
- Rank those parts using exact, deterministic calculations.
- Treat negative stock and extreme valid inputs correctly.
- Keep domain calculations isolated from HTTP and persistence.
- Support hundreds or thousands of parts with a simple, testable design.

## Non-goals

- Allocate a limited purchasing budget.
- Use unit cost as a ranking input.
- Recommend purchase quantities or create purchase orders.
- Manage suppliers, warehouses, reservations, or stock movements.
- Provide authentication or authorization.
- Introduce cache, queues, background jobs, CQRS, or external APIs.
- Define a cloud deployment.

## Domain model

A `Part` contains:

| Field | JSON type | Domain type | Required | Invariant |
| --- | --- | --- | --- | --- |
| `id` | string | UUID | Response only | Generated by the service and immutable |
| `name` | string | string | Yes | Trimmed value must not be empty; maximum 200 Unicode characters |
| `category` | string | string | Yes | Trimmed value must not be empty; maximum 100 Unicode characters |
| `currentStock` | integer | signed 64-bit integer | Yes | Negative values are allowed |
| `minimumStock` | integer | signed 64-bit integer | Yes | Must be greater than or equal to zero |
| `averageDailySales` | number | exact decimal | Yes | Must be greater than or equal to zero |
| `leadTimeDays` | integer | signed 32-bit integer | Yes | Must be greater than or equal to zero |
| `unitCost` | number | exact decimal | Yes | Must be greater than or equal to zero and have at most two fractional digits |
| `criticalityLevel` | integer | integer | Yes | Must be between 1 and 5, inclusive |

The service trims `name` and `category` before validation and persistence.
Categories are case-sensitive stored values and are not restricted to a fixed
enumeration.

`createdAt` and `updatedAt` may be stored as persistence metadata but are not part
of the v1 public part representation.

## Functional requirements

- **FR-001:** The service must create a part from a valid request and generate its
  UUID.
- **FR-002:** The service must return one part by UUID.
- **FR-003:** The service must return a paginated list of parts.
- **FR-004:** The part list must support an optional exact category filter.
- **FR-005:** The service must fully replace the mutable fields of an existing
  part.
- **FR-006:** The service must permanently delete an existing part.
- **FR-007:** The service must return only parts that require restocking, ordered
  by priority.
- **FR-008:** The service must expose liveness and database readiness endpoints.
- **FR-009:** The service must persist parts in PostgreSQL through an
  application-owned `PartRepository` abstraction.
- **FR-010:** The service must return errors using the error envelope defined by
  this specification.

## Business rules

- **BR-001:** Expected consumption must be calculated as:

  ```text
  expectedConsumption = averageDailySales × leadTimeDays
  ```

- **BR-002:** Projected stock must be calculated as:

  ```text
  projectedStock = currentStock - expectedConsumption
  ```

- **BR-003:** A part requires restocking if and only if:

  ```text
  projectedStock < minimumStock
  ```

- **BR-004:** For a part that requires restocking, urgency score must be:

  ```text
  urgencyScore = (minimumStock - projectedStock) × criticalityLevel
  ```

- **BR-005:** Results must be ordered by `urgencyScore` descending.
- **BR-006:** Equal urgency scores must be ordered by `criticalityLevel`
  descending.
- **BR-007:** Results still tied must be ordered by `averageDailySales`
  descending.
- **BR-008:** Results still tied must be ordered by `name` ascending using a
  case-insensitive Unicode comparison. The original name is the secondary name
  comparison when folded names are equal.
- **BR-009:** Results still tied after all specified business criteria must be
  ordered by UUID ascending to guarantee deterministic output.
- **BR-010:** Current stock must not be clamped to zero. Negative current and
  projected stock participate normally in the formulas.
- **BR-011:** Zero average daily sales and zero lead time are valid and produce
  zero expected consumption.
- **BR-012:** Exact decimal arithmetic must be used for calculations and equality
  comparisons.
- **BR-013:** `unitCost` must be stored and returned but must not affect restock
  eligibility or priority.
- **BR-014:** The written formulas in this specification take precedence over the
  inconsistent numeric example in the original challenge.

## API conventions

- Request and response media type is `application/json`, except successful
  deletion responses, which have no body.
- UUID path parameters must use canonical UUID syntax.
- Request bodies must reject unknown fields and trailing JSON values.
- Decimal values are JSON numbers.
- A validation error may report more than one invalid field.
- Unexpected internal details must not be exposed.
- The contract described here is also published as an OpenAPI 3.0 document,
  `api/openapi.yaml`, served at `GET /openapi.yaml` with a Swagger UI at `GET /docs`.
  Both are served from assets embedded in the binary, so they need no network access.
  This specification remains the source of truth: the document describes the same
  contract for tooling, and a test fails if it and the router disagree.

### Error envelope

All non-health error responses use:

```json
{
  "error": {
    "code": "validation_error",
    "message": "the request contains invalid fields",
    "fields": {
      "criticalityLevel": "must be between 1 and 5"
    }
  }
}
```

`fields` is optional and appears only when field-level detail is useful.

Stable v1 error codes:

| HTTP status | Code | Use |
| --- | --- | --- |
| `400` | `invalid_request` | Malformed JSON, unknown fields, invalid UUID, or invalid query parameters |
| `400` | `validation_error` | Domain input violates one or more field invariants |
| `404` | `part_not_found` | The requested part does not exist |
| `404` | `not_found` | The requested path is not a route this service serves |
| `405` | `method_not_allowed` | The path exists but does not support the method |
| `413` | `request_too_large` | Request body exceeds the configured limit |
| `500` | `internal_error` | Unexpected application or dependency failure |
| `503` | `service_unavailable` | Readiness dependency is unavailable |

The two `404` codes are distinct on purpose. `part_not_found` means a part was looked up
by a valid identifier and does not exist. `not_found` means the request did not address a
route this service serves, so no part was looked up at all. Reporting `part_not_found`
for an unknown path would tell a client that a part is missing when the path is what was
wrong.

## API contracts

### Part write body

Creation and replacement accept all mutable fields:

```json
{
  "name": "Oil Filter X",
  "category": "engine",
  "currentStock": 15,
  "minimumStock": 20,
  "averageDailySales": 4,
  "leadTimeDays": 5,
  "unitCost": 18.50,
  "criticalityLevel": 3
}
```

### Part representation

```json
{
  "id": "cdb09c19-9aa0-4f11-a5d8-c496bc52927f",
  "name": "Oil Filter X",
  "category": "engine",
  "currentStock": 15,
  "minimumStock": 20,
  "averageDailySales": 4,
  "leadTimeDays": 5,
  "unitCost": 18.50,
  "criticalityLevel": 3
}
```

### `POST /parts`

- Accepts a part write body.
- Returns `201 Created` with the created part.
- Sets `Location` to `/parts/{id}`.
- Returns `400` for malformed or invalid input.

### `GET /parts/{id}`

- Returns `200 OK` with the part.
- Returns `400` when the ID is not a valid UUID.
- Returns `404` when no part has the ID.

### `GET /parts`

Supported query parameters:

| Parameter | Default | Rule |
| --- | --- | --- |
| `category` | absent | Exact match after trimming; empty values are invalid |
| `limit` | `50` | Integer from 1 through 100 |
| `offset` | `0` | Non-negative integer |

The stable default ordering is `name` ascending using the same name comparison
defined by `BR-008`, followed by UUID ascending.

Returns `200 OK`:

```json
{
  "items": [],
  "pagination": {
    "limit": 50,
    "offset": 0,
    "total": 0
  }
}
```

An empty result is successful and returns an empty `items` array.

### `PUT /parts/{id}`

- Accepts the complete part write body.
- Missing mutable fields are invalid; partial updates are not supported.
- The path UUID remains unchanged.
- Returns `200 OK` with the updated part.
- Returns `400` for an invalid UUID or body.
- Returns `404` when no part has the ID.
- Uses last-write-wins semantics; optimistic concurrency is outside v1.

### `DELETE /parts/{id}`

- Permanently deletes the part.
- Returns `204 No Content` with an empty body.
- Returns `400` for an invalid UUID.
- Returns `404` when no part has the ID.
- Repeating a successful deletion returns `404`.

### `GET /restock/priorities`

This endpoint has no v1 query parameters. It returns `200 OK`:

```json
{
  "priorities": [
    {
      "partId": "cdb09c19-9aa0-4f11-a5d8-c496bc52927f",
      "name": "Oil Filter X",
      "currentStock": 15,
      "projectedStock": -5,
      "minimumStock": 20,
      "urgencyScore": 75
    }
  ]
}
```

An empty ranking returns an empty `priorities` array.

### `GET /healthz`

- Returns `200 OK` while the process can serve HTTP.
- Does not query PostgreSQL.

```json
{
  "status": "ok"
}
```

### `GET /readyz`

- Performs a bounded PostgreSQL readiness check.
- Returns `200 OK` when the dependency is available.
- Returns `503 Service Unavailable` when the check fails or times out.

Successful response:

```json
{
  "status": "ready"
}
```

## Persistence requirements

- PostgreSQL is the v1 persistence adapter.
- The application owns a domain-oriented `PartRepository` interface.
- Persistence-specific types must not cross into application or domain APIs.
- Schema constraints must enforce non-negative minimum stock, sales, lead time,
  and unit cost, plus criticality from 1 through 5.
- The schema must not prohibit negative current stock.
- Category filtering requires an index appropriate for exact matches.
- Migrations must be ordered, versioned, and reproducible.
- Repository operations must accept a context and use parameterized SQL.

## Failure modes and edge cases

| Case | Expected behavior |
| --- | --- |
| Negative current stock | Accepted and used without clamping |
| Negative projected stock | Returned as calculated and used in urgency score |
| Zero sales | Expected consumption is zero |
| Zero lead time | Expected consumption is zero |
| Very high valid lead time | Exact calculation succeeds without integer or floating-point overflow |
| Projected stock equals minimum stock | Part is excluded |
| No parts need restocking | `200` with an empty priority array |
| Complete priority tie | UUID provides stable final order |
| PostgreSQL unavailable during CRUD or ranking | Generic `500`; internal cause is logged |
| PostgreSQL unavailable during readiness | `503` |
| Malformed JSON or unknown field | `400 invalid_request` |
| Domain invariant violation | `400 validation_error` |

## Acceptance criteria

- **AC-001:** Given a valid part body, creating it returns `201`, a generated UUID,
  a `Location` header, and the normalized part representation.
- **AC-002:** Given a persisted part, it can be retrieved, fully replaced, listed,
  and deleted through the documented contracts.
- **AC-003:** Given multiple categories, filtering returns only exact category
  matches and reports pagination metadata for the filtered result.
- **AC-004:** Given invalid fields, the service returns `400 validation_error`
  without persisting or replacing data.
- **AC-005:** Given a missing valid UUID, get, update, and delete return
  `404 part_not_found`.
- **AC-006:** Given current stock `15`, average daily sales `4`, lead time `5`,
  minimum stock `20`, and criticality `3`, ranking returns projected stock `-5`
  and urgency score `75`.
- **AC-007:** Given projected stock equal to minimum stock, the part is absent
  from the priority response.
- **AC-008:** Given negative current stock, the unchanged negative value
  contributes to projected stock and urgency.
- **AC-009:** Given zero sales or zero lead time, expected consumption is zero and
  eligibility is determined from current stock.
- **AC-010:** Given scores tied at each successive criterion, results follow
  criticality, sales, name, and UUID ordering in that order.
- **AC-011:** Given fractional average sales, calculation and tie comparison use
  exact decimal values.
- **AC-012:** Given no eligible part, the endpoint returns `200` and
  `{"priorities":[]}`.
- **AC-013:** Given an unavailable database, liveness remains `200` while readiness
  returns `503`.
- **AC-014:** Given malformed JSON, an unknown field, a trailing value, or an
  oversized body, the service returns the documented client error.
- **AC-015:** Given the same persisted dataset, repeated priority requests return
  the same order and values.
- **AC-016:** Given two parts with different unit costs but identical ranking
  inputs, unit cost does not alter eligibility or priority.

## Test strategy

- **Domain unit tests:** table-driven coverage of every formula, threshold,
  negative value behavior, decimal calculation, and ordering criterion.
- **Application tests:** coverage for CRUD orchestration, missing resources, and
  dependency errors, over the in-process repository in `internal/adapter/memory` plus a
  small explicit stub for the failure paths.
- **HTTP tests:** `httptest` coverage for payload parsing, validation, query
  parsing, status codes, headers, envelopes, and empty collections.
- **PostgreSQL statement tests:** the SQL the adapter builds, asserted under GORM's
  `DryRun` without contacting a server, plus round-trip coverage of the record mapping.
  This is what guards a full replacement writing every mutable column, including zero
  values.
- **PostgreSQL integration tests:** migrations, CRUD against a real instance, category
  filtering, pagination, constraints, and context-aware repository operations. Not yet
  automated; see the manual verification below.
- **End-to-end test:** create multiple parts through HTTP and verify the complete
  priority response and ordering.

### Manual verification against PostgreSQL

Automated integration tests against a real PostgreSQL instance are the one test level
from the strategy above that is not yet implemented, so the behaviour that only appears
with a real database was verified by hand on 2026-07-28 against the compose stack. Each
step is reproducible with `make docker-up`.

| Behaviour | Command | Result |
| --- | --- | --- |
| Migrations apply in order before the API serves traffic | `docker compose up` | `00001` then `00002`, then the API starts |
| The five CHECK constraints exist and reject invalid rows | direct `INSERT` of `criticality_level=9`, `minimum_stock=-1`, `unit_cost=-5` | each rejected by its named constraint |
| Negative current stock is accepted by the schema (BR-010) | direct `INSERT` of `current_stock=-999` | accepted |
| Full replacement writes zero values | `PUT` with `currentStock=0`, `minimumStock=0`, `leadTimeDays=0`, then `GET` | all three stored as `0` |
| Replacement preserves `created_at` and advances `updated_at` | `SELECT created_at < updated_at` after the `PUT` above | true, and `created_at` retained |
| AC-006 over the wire, decimals unquoted | `GET /restock/priorities` | `"projectedStock":-5, ..., "urgencyScore":75` |
| Liveness and readiness diverge when the database stops (AC-013) | stop PostgreSQL, then probe both | `/healthz` `200`, `/readyz` `503` |
| A dependency failure returns the envelope and logs the cause | `GET /parts` with PostgreSQL stopped | `500 internal_error`, cause logged with the request ID |
| Startup fails rather than serving without persistence | start the API with PostgreSQL down | exit code `1`, nothing bound to the port |
| Graceful shutdown on `SIGTERM` | `docker compose stop api` | `shutting down` then `shutdown complete` |

### Deferred from v1 delivery

These were in the task list above and are deliberately not delivered. They change no
documented behaviour.

- Automated PostgreSQL integration tests and an automated end-to-end test.
- A continuous integration workflow.
- Connection pool limits and validated, configurable timeouts.

## Rollout and compatibility

This is the first public version, so no data migration from an earlier service or
backward-compatible API transition is required. PostgreSQL migrations must
complete before the API begins accepting traffic.
